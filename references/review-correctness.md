# 正确性评审（九项）

E2E 证明的是"我测的那几条路径对了"，不是"这段代码是对的"。这九项是 E2E 的盲区，也是生产事故的常见来源。

**逐项给结论，不许写"整体来看结构清晰"。**

## 每条结论的格式

```
<文件>:L<行> | <严重级别> | <问题> | <理由>
```

严重级别：`blocker` / `major` / `minor` / `ok` / `未覆盖`

**`未覆盖` 是合法且有价值的结论。** 假装看过比承认没看更糟。

## 九项

### 1. 事务边界与部分失败
写了一半失败会留下什么？有没有"扣了钱没发货"这类中间态？

### 2. 幂等
重复提交、重复回调、重试——会不会做两遍？

### 3. 并发
同一个资源被两个请求同时修改，最后是什么状态？有没有丢失更新？

### 4. 空值与边界
`null` / 字段缺失 / `[]` / `0` / 空字符串 / 超长字符串 / 负数。哪些会崩？

### 5. 错误路径
下游超时、上游 5xx、第三方返回脏数据。异常被吞了吗？用户看到什么？

### 6. 权限粒度
越权：改个 id 能不能读别人的数据？列表接口会不会漏过滤？

### 7. 资源泄漏
连接、文件句柄、监听器、定时器、订阅。异常路径上会释放吗？

### 8. N+1 与查询爆炸
循环里查询、无上限的 `in`、没有分页的全量加载。

### 9. 可观测性
线上出问题时，日志够不够定位？关键路径有没有埋点？错误有没有被静默 catch？

## 按 diff 路径分级

不是每个 diff 都值得九项全过。按**触及的路径**自动判定：

| diff 触及 | 档位 |
|---|---|
| 数据模型 / 迁移 / 事务 / 鉴权 / 并发 / 支付 / 上传 | **重档**：九项逐条 |
| 纯 UI / 样式 / 文案 / 配置 | **轻档**：只查 1（无）、5（错误提示）、9（日志） |
| 混合 | 按重档 |

## 三条禁止

1. **禁止评审自己设计的部分。** 谁设计的，就不能由谁审——那会退化成确认。
2. **禁止给"通过"当结论。** 结论只有两种：`blocked: <N> 个问题` 或 `clean（附未覆盖项）`。
3. **禁止顺手改代码。** 这一站只出清单。

## 通过的标准

- 没有 `blocker`
- `major` 已确认可接受或已排期
- `未覆盖` 项已明确标出，交给人判断是否补

**"E2E 全绿"不是通过的证据。** 它只说明被覆盖的路径没炸。
