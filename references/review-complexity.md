# 复杂度审计协议

只审**过度设计**。正确性、安全、性能**不在范围内**——那些交给 09 站，两边互不越界。

## 输出格式

每条一行：

```
<文件>:L<行> : <tag> <要删什么>. <用什么替代>.
```

tag 只有五个：

| tag | 含义 | 替代 |
|---|---|---|
| `delete:` | 死代码、没人用的配置、为想象中需求写的分支 | 什么都不用 |
| `stdlib:` | 手写了标准库已有的东西 | 点名那个函数 |
| `native:` | 依赖或代码在做平台已经做的事 | 点名那个特性 |
| `yagni:` | 只有一个实现的抽象、没人设的配置、只有一个调用方的层 | 摊平它，直到出现第二个 |
| `shrink:` | 同样逻辑更少的行数 | 给出更短的形式 |

**结尾必须给一个数字**：`net: -<N> lines possible`
如果确实没啥可删：`Lean already. Ship.`

## 好坏对比

❌ 「这个校验类可能有点复杂，考虑下是不是所有规则现在都需要？」

✅ `L12-38: stdlib: 27 行邮箱校验类. "@" in email 一行就够，真正的校验是确认邮件.`

✅ `L4: native: 为了一个格式化调用引入 moment. Intl.DateTimeFormat，0 依赖.`

✅ `repo.py:L88: yagni: 只有一个实现的 AbstractRepository. 摊平，等第二个实现出现再抽象.`

## 边界（很重要）

- **只列，不改。** 这一站不写代码。
- **单条 smoke test / assert 不算冗余**，不要建议删。
- **不评论风格、命名、注释。** 那些不是复杂度。
- **发现正确性问题时不要在这里展开**：写一行「疑似正确性问题，转 09」，然后停手。

## 为什么这条边界必须硬

便宜模型跑这一站会倾向于"能删就删"，而**防御性代码看起来最像冗余**。一次空值判断、一次权限复查、一个重试上限，都可能被标成 `delete:`。

所以：**这里的产出是提议，不是执行令。** 任何 `delete:` 建议在执行前必须被 09 站或人确认一遍。

## 判读结果

| 净删行数 | 判读 |
|---|---|
| 大量（>100） | 要么实现站过度建设，要么这一站误伤，逐条看 |
| 少量（<20） | 正常 |
| `Lean already` | 留意：少不代表对，只代表没找到冗余 |

**不要为了让它好看而把 N 做大。** 一个准确的 3 行，好过一个勉强的 30 行。
