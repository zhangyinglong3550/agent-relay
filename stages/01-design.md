# 01 方案设计（前端 / 后端）

**角色**：`design_fe` 或 `design_be`（能力档 high）
**输入**：`handoff/00b-scope.md`
**依赖变量**：`SIDE` = `frontend` | `backend`
**输出**：`handoff/0N-*-design.md` + `skeleton/` 下的可编译骨架

## 核心要求：交付可执行的约束，不是散文

下游是实现站，而且**不一定是同一个模型**。它不会去猜你的意图，只会照你写的东西做。散文只能写"为什么"，不能只写"为什么"。

所以每份方案必须同时交付两样东西：

1. **文档**：为什么这么设计、否决了什么、风险在哪
2. **骨架**：能编译通过的空壳。类型、接口签名、目录、路由表、DTO、错误码常量

**骨架编译不过，下游不许开工。** 这条是硬门槛。

## 文档必含

| 小节 | 内容 | 不写的后果 |
|---|---|---|
| 文件清单 | 新建/修改哪些文件，各自职责 | 实现站自己发明目录结构 |
| 数据结构 | 表、字段、索引、迁移；或前端 state 形状 | 两边各自造一份 |
| 状态机 | 有哪些状态、谁能改、非法转移怎么办 | E2E 写不出用例 |
| 错误码表 | 码、含义、前端如何分支 | 前端只能弹"操作失败" |
| 关键决策 | 至少 2 条被否决的替代方案 + 理由 | 评审无法判断你是否想过 |
| 风险 | 你拿不准的地方，明确标出来 | 埋雷给别人 |

## 骨架必含

- 目录结构（真实创建，不是示意）
- 类型 / 接口 / 函数签名，**实现可以是 `throw new Error("unimplemented")`**
- 常量：错误码、枚举、路由名
- 一个能跑通编译/类型检查的命令，并证明它通过

## 边界约定

- **只设计 `SIDE` 这一侧。** 对侧的接口按 `scope` 推演，不许偷偷定义对方。
- **不实现业务逻辑。** 骨架里出现真实现，说明你在替实现站干活，会让它无脑照抄。
- **明确标出你需要对侧确认的点**，写成「待契约确认」。

## 验收（下游可判定的程度）

- [ ] 一个不了解背景的工程师，只读这份文档，能说出要建哪些文件
- [ ] 骨架能在干净环境里编译/类型检查通过
- [ ] 每条错误码都有触发条件
- [ ] 没有「视情况」「类似上面」这类模糊指代
- [ ] 能从中直接写出至少 3 条 E2E 用例（做不到说明太虚）

## 不要做

- 不要改 `scope` 的范围。发现有缺口，写进文档的「风险」，不要自己扩张
- 不要写测试
- 不要为了让文档好看而省略实现细节（签名、字段名、枚举值必须精确）
