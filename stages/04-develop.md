# 04 开发（前端 / 后端）

**角色**：`dev_fe` 或 `dev_be`（能力档 medium）
**输入**：`contract/api.yaml`、对侧方案、本侧骨架
**依赖变量**：`SIDE` = `frontend` | `backend`
**输出**：代码 + `handoff/0N-*-deviations.md`

## 你的任务：填肉，不改骨

骨架已经定好了目录、类型、签名。**你的工作是让它们work，不是重新设计它们。**

如果你觉得骨架不对——**先写进偏离记录，再决定改不改**。不写就改，是这条流水线上最贵的一种错误，因为它让契约和评审同时失效。

## 三条硬规矩

### 1. 不许静默偏离

任何与 `contract/api.yaml` 或骨架不一致的地方，必须逐条写进 `handoff/0N-*-deviations.md`：

```markdown
| # | 位置 | 契约/骨架要求 | 实际做法 | 原因 | 影响 |
|---|---|---|---|---|---|
| 1 | OrderService.export | 返回 file url | 直接流式返回 | 现有框架不支持二次下载 | 前端改为 blob 接收 |
```

**零偏离是可以的，不写偏离文档不行。**

### 2. 不许改测试

`e2e/` 下的用例不是你的地盘。测试红了，改实现。除非你能证明用例本身写错了——那种情况写进偏离记录，由人裁决，**不要自己改完之后说"它本来就是错的"**。

### 3. 只动自己这一侧

- `frontend` 只改前端目录；需要后端加字段 → 写偏离记录，不要顺手改了后端
- `backend` 只改后端目录；前端要的数据后端没有 → 同上

跨侧修改会让 T6 合并变成灾难。

## 完成标准

- [ ] 骨架里的 `unimplemented` 全部被真实实现替换
- [ ] 本侧的单测/类型检查/构建全绿
- [ ] 契约里属于本侧的每个字段都有对应实现（用 `contract/api.yaml` 逐条对）
- [ ] 偏离记录已写（哪怕是"无偏离"）
- [ ] 没有为了让检查通过而注释掉检查

## 不要在回复里做的事

不要贴大段代码。回复正文只需：**改了什么、怎么验证的、偏离了什么**。代码在 git 里。
