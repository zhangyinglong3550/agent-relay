# 03 契约冻结 ⛩

**类型**：人工闸门（唯一的裁决点）
**输入**：`handoff/01-fe-design.md`、`handoff/02-be-design.md`
**输出**：`contract/api.yaml`、`contract/checklist.md`

## 为什么必须是人不放行

契约是全流程的**唯一真相源**。它错了，后面四个站全是无效劳动——而且是并行的无效劳动。

两个模型各自设计时必然在接口上分叉，谁对谁错不是技术问题，是产品选择。所以这里不设自动裁决。

## 要做什么

1. 读两份方案，找出**冲突点**（同一个东西被定义了两遍，且不一样）
2. 逐条裁决，写进 `contract/api.yaml`
3. 按 `references/contract-checklist.md` 的八项过一遍
4. 把裁决理由记在 `contract/checklist.md` 里——三个月后你会需要它

## 裁决原则

| 冲突类型 | 怎么裁 |
|---|---|
| 命名风格不一致 | 跟项目现状，不跟任何一方的偏好 |
| 字段多一个少一个 | 按 `scope` 的验收标准倒推，不需要的删掉 |
| 同步 vs 异步 | 按 `scope` 的量级决定，不按实现难度 |
| 状态机不一致 | **优先采用状态更少的那个**，多的状态通常是想象的 |
| 两边都说"我问过你" | 你没错过什么，是它们在猜。以 `scope` 为准 |

## 八项检查（缺一项不许放行）

1. 数据模型与枚举全集
2. 错误码与 HTTP 状态码映射
3. 鉴权粒度、无权限时的返回（403 还是 404）
4. 分页、排序、默认值
5. 时间与数字格式（**统一 ISO 8601 字符串**，不要 unix 秒）
6. 空值语义：`null` / 字段缺失 / `[]` 三者的区别
7. 幂等与并发：重复提交怎么办
8. 取消、超时、重试语义

细节见 `references/contract-checklist.md`。

## 出口

- [ ] `contract/api.yaml` 已写，且是**机器可读**的（能生成 schema、能跑契约测试）
- [ ] 八项逐条在 `contract/checklist.md` 打了勾
- [ ] 所有冲突有裁决记录
- [ ] 两份方案里标「待契约确认」的点，全部在这里有了答案

## 不要做

- 不要在这站修改任何业务代码
- 不要允许"先实现，回头再对齐契约"——那等于取消这一站
